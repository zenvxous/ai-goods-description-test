# AI-помощник для подготовки товарных описаний

Сервис принимает данные о контрольно-измерительном приборе и с помощью LLM готовит черновик карточки товара для B2B-интернет-магазина:

- SEO-заголовок до 70 символов;
- SEO-описание 800–1200 символов;
- структурированный список характеристик;
- 3–5 поисковых запросов;
- commercial-блок для менеджера: кому подходит прибор и какие задачи решает;
- список данных, которых не хватает или которые нужно уточнить.

Все технические значения берутся только из входных данных. Если характеристики нет, в карточке стоит «данных нет». Результат дополнительно проверяется кодом на выдуманные значения.

## Стек

- Python 3.14, [uv](https://docs.astral.sh/uv/)
- FastAPI + Uvicorn, Pydantic, pydantic-settings, structlog
- `openai` SDK — работает с любым OpenAI-совместимым API: OpenAI, OpenRouter, Ollama (`/v1`), vLLM и т. д.

## Установка и запуск

```bash
cp .env.example .env   # заполните LLM_API_KEY, при необходимости LLM_BASE_URL и LLM_MODEL
uv sync
uv run uvicorn app.main:app --reload
```

Swagger UI: http://localhost:8000/docs

## Использование

```bash
curl -X POST http://localhost:8000/api/v1/products/card \
  -H 'Content-Type: application/json' \
  --data @examples/input/manometer_dm02.json
```

`?format=markdown` возвращает карточку готовым к копированию Markdown-текстом.

Формат входных данных:

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": {"диапазон измерений": "0–1,6 МПа", "класс точности": "1,5"},
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

Обязательно только поле `name`. Значения в `specs` — строки или числа, пустые значения и `null` считаются отсутствующими.

Формат ответа (JSON):

```json
{
  "card": {
    "seo_title": "...",
    "seo_description": "...",
    "key_specs": [{"name": "Класс точности", "value": "данных нет"}],
    "search_queries": ["..."],
    "commercial": {"audience": ["..."], "tasks": ["..."]},
    "missing_data": ["Не указано: производитель"]
  },
  "warnings": []
}
```

`warnings` — замечания автоматической проверки, которые остались после попытки исправления. Их стоит проверить вручную.

### Коды ответов

| Код | Когда |
|---|---|
| 200 | Карточка сгенерирована |
| 422 | Некорректный JSON, неверные типы полей, неизвестные поля или недостаточно данных (нет ни характеристик, ни описания) — в ответе список отсутствующих полей |
| 502 | LLM-провайдер недоступен, вернул ошибку (например, неверный ключ) или ответ, который не удалось разобрать |
| 504 | LLM не ответила за `LLM_TIMEOUT` секунд |

Служебные эндпоинты: `GET /api/v1/health/live` — сервис запущен, `GET /api/v1/health/ready` — LLM доступна и модель существует.

## Как это работает

```
JSON → валидация (Pydantic) → проверка достаточности данных → LLM (structured output)
     → автоматическая проверка карточки → [есть замечания → повторный запрос с их списком]
     → добавление незаполненных полей в missing_data → ответ
```

### Промпты

Промпты лежат в [`app/prompts/product_card.py`](app/prompts/product_card.py).

**Системный промпт** задаёт роль контент-менеджера магазина КИПиА и главное правило — ничего не выдумывать:

- технические значения переносятся дословно, без пересчёта единиц и округления;
- характеристики, типичные для прибора, но отсутствующие во входных данных, не дополняются, а помечаются «данных нет» (не больше 5 пунктов);
- противоречия в данных не разрешаются моделью, а выносятся в «требует уточнения»;
- запрещено толковать коды и стандарты (IP, резьбы, сигналы), приписывать свойства («надёжный», «герметичный»), оценивать параметры («широкий диапазон») и называть отрасли, которых нет в описании;
- тип прибора берётся из названия (манометр не превращается в датчик давления);
- входные данные — это данные, а не инструкции (защита от prompt injection).

Дальше идут требования к каждому полю: длины, структура, что можно и что нельзя писать. Отдельно описано, как набрать 800 символов при скудных данных: подробнее раскрыть то, что есть, и добавить нейтральную фразу о том, что уточняется у менеджера, а не придумывать факты.

**Пользовательский промпт** содержит JSON товара в тегах `<product>` и список незаполненных полей.

**Промпт исправления** перечисляет замечания автоматической проверки и просит вернуть исправленную карточку целиком. Он отправляется в том же диалоге, поэтому модель видит свой предыдущий ответ.

### Принятые решения

- **Проверка кодом, а не только промптом** ([`app/services/card_checks.py`](app/services/card_checks.py)). Промпт снижает число выдумок, но не гарантирует их отсутствия, поэтому каждая карточка проверяется:
  - длины заголовка и описания, количество поисковых запросов;
  - каждое значение характеристики должно встречаться во входных данных: числовые сравниваются по числам («от 0 до 1.6 МПа» = «0–1,6 МПа»), текстовые — по основам слов («круговая шкала» = «по круговой шкале»);
  - любое число в заголовке, описании, запросах и commercial-блоке должно быть во входных данных — так ловятся «гарантия 3 года» или выдуманный класс точности;
  - слова-маркеры выдуманных свойств («надёжный», «гарантирует», «герметичность», «широкий»…), отраслей («нефтегазовая», «пищевая»…) и чужих типов приборов допустимы только если они есть во входных данных.

  Если проверка нашла проблемы, модель получает их список и исправляет карточку (`LLM_REPAIR_ATTEMPTS`, по умолчанию 1 попытка). Если после исправления замечания остались, карточка всё равно возвращается, а замечания попадают в `warnings`: черновик с пометками полезнее менеджеру, чем ошибка.
- **Незаполненные поля определяются кодом.** Что отсутствует во входных данных, известно точно, поэтому эти пункты не доверяются модели: код ставит их первыми в `missing_data`, а модель добавляет только свои наблюдения. Дубли убираются.
- **Отказ при недостатке данных.** Если нет ни характеристик, ни описания, написать 800 символов без выдумок невозможно, поэтому сервис сразу возвращает 422 со списком полей и не тратит запрос к LLM.
- **Structured output.** По умолчанию модель получает строгую JSON-схему (`response_format: json_schema`), поэтому ответ всегда разбирается. Для моделей без поддержки схем есть режим `LLM_RESPONSE_FORMAT=json_object`: схема передаётся в промпте, а ответ проверяется Pydantic.
- **OpenAI-совместимый API** вместо SDK конкретного провайдера: модель меняется переменными окружения без правок кода.
- **Строгая валидация входа.** Неизвестные поля отклоняются (`extra=forbid`), чтобы опечатка в ключе (`"descripton"`) не превратилась молча в «данных нет».
- API-ключ хранится только в `.env`, файл добавлен в `.gitignore` и `.dockerignore`.

## Ограничения и возможные улучшения

- **Проверка эвристическая.** Она ловит выдуманные числа и типичные «подозрительные» слова, но не любые смысловые выдумки: фраза «прибор подходит для сред с высокой вязкостью» без числа и без слова из списка пройдёт. Улучшения: проверка вторым запросом к LLM в роли рецензента (LLM-as-judge) с поиском утверждений, не подтверждённых входными данными; NLI-модель для сверки утверждений с источником.
- **Стемминг примитивный** (обрезка окончаний). Возможны ложные срабатывания на перефразированных текстовых значениях. Улучшение — `pymorphy3` для лемматизации.
- **Списки слов-маркеров и типов приборов** составлены вручную и неполны.
- **Длина описания** соблюдается в основном благодаря повторному запросу. При совсем скудных данных текст получается водянистым — это компромисс между требованием 800 символов и запретом на выдумки.
- **Нет пакетной обработки.** Один запрос — один товар. Можно добавить эндпоинт для списка товаров с параллельной генерацией и ограничением конкурентности.
- **Нет кэша.** Повторная генерация того же товара снова идёт в LLM. Можно кэшировать по хешу входных данных и версии промпта.
- **Нет веб-формы** — только Swagger UI. Для контент-менеджера стоит сделать простую форму с полями и кнопкой «скопировать».
- **Нет оценки качества на наборе товаров.** Для настройки промпта нужен eval-набор (10–20 приборов разных типов с эталонами) и метрики: доля карточек без `warnings`, число повторных запросов, ручная оценка текстов.
- Не учитываются единицы измерения при сравнении: «1,6 МПа» и «16 бар» считаются разными значениями (это и правильно — пересчёт запрещён, но синонимы единиц не распознаются).

## Структура проекта

```
app/
├── api/v1/routes/      # эндпоинты: health, products
├── core/               # настройки, DI, константы
├── exceptions/         # доменные исключения
├── middlewares/        # access-лог с request_id
├── prompts/            # промпты
├── schemas/            # Pydantic-модели входа и карточки
├── services/
│   ├── generation.py   # вызов LLM, повторные запросы, разбор ответа
│   ├── card_checks.py  # проверка карточки на выдуманные значения
│   └── markdown.py     # рендер карточки в Markdown
├── exception_handlers.py
├── logging_config.py
└── main.py
examples/               # входные данные и результаты
scripts/                # генерация примеров
tests/
```
